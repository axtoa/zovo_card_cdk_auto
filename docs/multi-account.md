# 多账号卡台接入

## 使用方式

1. 后台「卡台接入」管理多个账号，分别填写名称、API Key 和回调密钥。原有配置自动迁移为「原账号」。账号使用同一卡台站点。
2. 在「CDK 卡密」选择账号，再查看库存或发码。多账号时必须明确选择；没有全站当前账号或启停开关。
3. 已发卡密永久归属发码账号。兑换、查单、坏卡排除、失败补发均按原账号处理。新账号不会接管其他账号的费用。
4. 「卡台接入」分别展示可消费余额、总余额、保证金和最后成功更新时间。可单独或全部刷新；失败保留旧数据并显示错误。
5. 所有账号使用相同回调地址 `/api/v1/webhooks/cardplatform`，但使用各自的 Webhook Secret。更换密钥时旧密钥保留 24 小时用于在途通知，之后自动失效。回调签名确定来源，不信任请求自行声明的账号编号。
6. 选卡优先级、兑换策略和坏卡判定阈值全站共用。保存选卡规则会同步所有账号，并列出成功/失败结果；「重新同步全部账号」可重试。产品缓存及实际坏卡记录分别保存。

## 数据与接口约束

- 管理接口通过 `X-Card-Account-ID` 明确传入账号。未选择或无效账号返回 400。账号上下文仅属于本次请求；不使用全局可变配置。
- API Key 不返回前端。账号 Key 一经配置不能换成另一个 Key，也不提供删除账号入口，避免旧库存和在途订单失去访问权限。新增账号先调用只读余额接口验证 Key。
- 浏览器缓存使用账号隔离的新命名空间。旧缓存不自动认领到某账号；「同步完整码」从该账号的卡台接口取权威数据。
- 上游编号允许在不同账号重复。备注、状态、区域、失败事件、黑名单和产品缓存均以账号隔离。
- 完整卡密归属不可更改。公开兑换接口不发送 API Key；通过已验证预览建立的 token → 卡密映射确定本地归属。未知来源码仍可由卡台公开接口判断，但不借用其他账号的查单权限或黑名单。
- 回调按账号隔离幂等键；数据库失败返回非 2xx，待重试完成后才标记已处理；迟到的 unused/reserved 不覆盖 consumed/disabled。
- 补发固定使用原账号、套餐和付款地区；无法核对订单或付款地区时不补发。补发请求使用基于旧码的稳定幂等键。
- 共用卡台站点在配置账号后固定。不能用修改环境变量将既有卡密静默指向另一个平台。

## 升级与回滚

首次启动使用一个 SQLite 事务迁移旧配置和库存。迁移可重复运行；任何失败都会阻止服务启动，避免部分迁移后继续发码。上线前应先停止旧服务并备份整个数据目录。升级后新增的多账号业务不可交给旧版程序处理；回滚需恢复升级前数据库备份，并先处理升级后已产生的业务，不能仅退回旧镜像。

本地验证包括旧库存迁移、跨账号相同编号隔离、并发余额请求、共享回调验签/重复/乱序/重试、历史 token 归属、原账号补发，以及模拟卡台浏览器操作。真实卡台账号的 IP 白名单、余额和上游权限仍以部署环境实测为准。

## 补发异常与人工核对

购买补发码前，`agent_exchange_attempts` 会保存原码哈希、账号和请求状态。上游超时、返回异常、新码落库失败或旧码禁用失败时，不自动再购买；接口明确提示联系管理员。该保护在进程重启后仍生效，不依赖卡台幂等键永久有效。

管理员应按审计日志中的账号和新旧码编号核对卡台订单、收费记录与库存。已成功生成的新码可在原账号库存中同步；确认旧码已禁用并完成记录后再交付。`issued` 状态保存了已返回的新码，`requested` 状态表示结果尚未确认。不要为了重试而直接删除请求记录；无法确认上游是否已经扣费或发码时，应先联系卡台核对。
